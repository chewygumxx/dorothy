# Dorothy's memory evaluation design

## Purpose

Her memory has never been measured, and the user judges it weak
([open-source replacements](../notes/2026-10-18_open-source-replacements.md#memory)).
The [memory contract](./2026-10-18-memory-contract-design.md) put every
engine behind one interface and named the evaluation as the piece that
chooses what sits there: her memory as it is, improved, or a provider
such as Hindsight. This spec defines that evaluation: what it asks, of
what, how it scores, and what it reports.

It measures access, the second of the memory's priorities, on her own
data; compatibility is the contract's, and the evaluation checks only
that a system can sit behind it.

## Decisions

Taken on 2026-10-18 by the coding agent, on the user's standing
delegation to approve in their stead:

| Question | Decision | Why |
| --- | --- | --- |
| Where it lives | A new package, `@dorothy/eval`, run with `bun run eval` | A tool for her builders, not a mode of hers; nothing imports it |
| Data | A snapshot: her data directory copied into a work directory, every root passed in | Nothing it does can touch the archive; runs repeat on one copy |
| Questions | Mined where her data already holds the answer, generated by a model for LongMemEval's types, every generated one reviewed by the owner | Mined questions are real and free; generated ones cover what mining cannot |
| Systems | One small interface; her baseline engine, a lexical bound and a full-context bound first | Providers and an improved Dorothy follow with their own specs, meeting the same interface |
| Answering | One retrieval budget for every system, no tool loop, the same answering model | Holds all but the system constant, as the note's design asks |
| Models | OpenAI-compatible Chat Completions, a base URL and model per role, keys named by variable | A standard protocol, any provider or a local server; subscription OAuth is for Claude Code |
| Judging | openevals' LLM-as-judge, strict and lenient, a model family apart from the answering one | Adopted, not bespoke, as the protocol-diversity minutes rule |
| Without a key | Retrieval metrics run with no model at all | The first numbers need nothing but her data |

Rejected: a public benchmark alone, which says nothing of her data; an
agentic run where each model drives the MCP tools, which mixes the
model's skill with the system's (later, as a second mode); and
LangSmith, which openevals does not need.

## Architecture

Six units in `packages/eval`, each a directory:

1. **Snapshot** (`snapshot/`): copies a data directory into
   `<work>/data/dorothy` and gives the environment that points every
   root into the work directory.
2. **Questions** (`questions/`): the question file's format, mining,
   generation and the review loop.
3. **Systems** (`systems/`): the interface and its first three
   implementations.
4. **Models** (`models/`): the roles, their configuration, and the one
   client that calls them.
5. **Runner** (`run/`): asks every question of every system, answers,
   judges and records.
6. **Report** (`report/`): metrics from a run's records, its Markdown
   report, and a comparison of runs.

`@dorothy/eval` depends on `core` and `memory`. `memory` gains one entry
point, `@dorothy/memory/evaluation`, for what the evaluation reads of the
archive: the baseline engine over a given environment, the
conversations' text, the knowledge files, and her appraised reads. The
evaluation reads no file of memory's itself.

## The snapshot

```sh
bun run eval -- snapshot --from ~/.local/share/dorothy --work ~/eval
```

- `--from` is a data directory (`$XDG_DATA_HOME/dorothy`), always given,
  so that nothing reads her real data by default; `--work` a directory
  of the user's choosing, made if missing, refused if it holds a
  snapshot already unless `--replace` is given. Neither may hold the
  other.
- It copies `transcripts/` (conversations and their sidecars),
  `knowledge/`, `facts/` where a data directory has not yet moved it,
  and `tags.json`, and records what it copied in `<work>/snapshot.json`:
  the source, the time, and counts of conversations and knowledge files.
  It never writes to `--from`, and copies no `.git`, mirror or token.
- Every later command takes `--work` and runs with `HOME`,
  `XDG_DATA_HOME`, `XDG_CACHE_HOME`, `XDG_STATE_HOME` and
  `XDG_CONFIG_HOME` under it, so recall's index is built fresh in the
  work directory, and history and the mirror stay off.
- The work directory holds her data in clear, and so do the questions
  and runs; the README says to keep it where her data directory is kept,
  and the evaluation never writes inside the repository.

## Questions

### The file

`<work>/questions.jsonl`, one question a line:

| Field | Meaning |
| --- | --- |
| `id` | A stable id, `q-` and eight hex digits of a hash of the question and its evidence |
| `type` | `single-session`, `preference`, `multi-session`, `knowledge-update`, `temporal`, `abstention` or `lookup` |
| `question` | The text asked |
| `answer` | The reference answer; none for a `lookup` |
| `evidence` | Contract ids that hold the answer: `c:<phrase>`, or `k:<path>`; none for `abstention` |
| `exclude` | A conversation the question came from, left out of retrieval; optional |
| `asOf` | The date the question is asked on, `YYYY-MM-DD` |
| `project` | The project it is asked in, a project's id; optional |
| `source` | `mined` or `generated`, and for generated the model |
| `status` | `draft`, `accepted` or `rejected` |
| `note` | The reviewer's note; optional |

Only accepted questions are run. A malformed line is reported with its
number: `run` skips it, while the commands that rewrite the file
(`mine`, `generate`, `review`) refuse until it is mended, so that none
drops a line the owner wrote. A file that cannot be read, other than for
being absent, stops those commands the same way.

### Mined lookups

Her `open` calls carry a purpose, and her next review appraises each
read as `none`, `slight`, `useful` or `essential`. Each read appraised
useful or essential is a real question with a known answer: the purpose
is the question, the opened conversation or knowledge file the evidence,
the reading conversation the `exclude`, and the read's date the `asOf`.
They have no reference answer, so they score retrieval alone. A read of
a hidden conversation or a retired file is passed over, as no system
reaches it. They are
mined accepted, as the appraisal is her own review; the owner may reject
one.

```sh
bun run eval -- mine --work ~/eval
```

Mining is repeatable: a question whose id exists is left as it is, so a
reviewer's decisions survive.

### Generated questions

A generating model drafts the other types from samples of the snapshot:

- **single-session**: one conversation's turns; the answer is in them.
- **preference**: her `user` and `feedback` knowledge, asked
  indirectly, as a request whose best answer the preference shapes.
- **multi-session**: two or three conversations sharing a tag or a
  project; the answer needs more than one.
- **knowledge-update**: a retired knowledge file beside the file that
  replaced it, or a conversation that revises an earlier one; the answer
  is the newer, and the older is named in the question's `note`.
- **temporal**: a conversation's dated turns; the answer is a date, an
  order or a span.
- **abstention**: a plausible question on nothing in the snapshot, which
  the answer must decline; a lexical search of the snapshot for its key
  terms must find nothing, or the draft is dropped. "Nothing" is a
  turn or file holding at least half the terms (two at the least).

```sh
bun run eval -- generate --work ~/eval --count 300
```

- Counts per type default to the shares of LongMemEval-S's 500
  questions, scaled to `--count`: single-session 126, preference 30,
  multi-session 133, knowledge-update 78 and temporal 133, with
  abstention 30 beside them. They can be given per type
  (`--type temporal=40`).
- The model returns JSON, checked by a schema; a draft whose evidence
  ids are not in the snapshot, or whose answer is empty, is dropped and
  counted.
- Samples are drawn by a seed, which `<work>/generated.json` records
  with the model, the counts asked and made, and the drafts dropped and
  why, so a generation can be repeated. Each generation adds an entry
  to that list, and the question file is read again just before the
  drafts join it, so a review meanwhile loses nothing.
- A failed call is dropped with its reason, a line with no key in it.
  Generation stops, keeping what it has made, at a 401 or a 403, at
  three failed calls in a row, or at `--max-calls`, and says why.

### Review

```sh
bun run eval -- review --work ~/eval
```

A terminal loop over drafts, one at a time: the question, its answer,
its evidence's titles and the passage it came from, then accept, edit
(the line in `$EDITOR`), reject with a note, skip or quit. Each decision
is written at once, so quitting loses nothing. The note on the evaluation
estimates three to five hours for 300.

## Systems

```ts
interface System {
    readonly name: string;
    // What it gives for a question within budget characters.
    retrieve(question: Asked, budget: number): Promise<Retrieved>;
    // For systems with a store of their own, as providers have.
    prepare?(): Promise<void>;
    close?(): Promise<void>;
}
type Asked = { text: string; asOf: string; project: string | null;
    exclude: string | null };
// Contract ids best first, for evidence recall, and the context the
// answering model reads.
type Retrieved = { ranked: string[]; context: string };
```

The first three are built over one corpus, the snapshot's archive
opened once for the run:

1. **`dorothy`**: her baseline engine over the snapshot. Its opening
   block for the question's project, then `search` over all scopes for
   the question, then `open` on the top hits, until the budget is spent.
   It is what a harness gets today, without a model choosing the calls.
   The block takes 40% of the budget and the hits the rest; its ranked
   ids are the hits, then what the block gave besides.
2. **`lexical`**: a bound from below. Every conversation turn and
   knowledge file scored by how many of the question's terms it holds,
   best first, no index: what plain `grep` would find.
3. **`full`**: a bound from above, where it fits. Every conversation and
   knowledge file, newest first, until a budget of its own
   (`--full-budget`, 400,000 characters by default, some 100,000
   tokens); its ranked ids are what fitted, so its evidence recall says
   how much of the snapshot that was.

`exclude` is honoured by all three. Retrieval sees the whole snapshot;
`asOf` dates the question for the answering model alone. A system that
fails a question records the error and yields nothing; the run goes on.
A failed retrieval spends no answer or judgement, and counts as a miss.

Later systems, each in its own spec: Dorothy improved (the engine
spec), Hindsight, OpenViking, EverOS and Honcho, each fed by replaying
the snapshot.

## Models

Three roles, set in `<work>/eval.toml`:

```toml
[models.generate]
base-url = "https://openrouter.ai/api/v1"
model = "deepseek/deepseek-v3.2"
key = "OPENROUTER_API_KEY"   # the variable holding the key, never the key

[models.answer]
base-url = "https://openrouter.ai/api/v1"
model = "openai/gpt-oss-120b"
key = "OPENROUTER_API_KEY"

[models.judge]
base-url = "https://openrouter.ai/api/v1"
model = "google/gemini-2.5-flash"
key = "OPENROUTER_API_KEY"
```

- A role's key is read from the named variable, which `dotenvx run`
  supplies from `.env`; a key is never written to a file, a log or a
  report. A local server (llama.cpp, Ollama) needs no key.
- The client is `@langchain/openai`'s `ChatOpenAI`, which openevals
  takes as its judge; one client for all three roles.
- Every call has a timeout and two retries on a 429 or 5xx; a call that
  still fails is recorded as failed, never fatal. The retries also
  cover a 408, a timeout and a lost connection, wait 2 seconds and then
  4, and each attempt spends one of `--max-calls`; a refusal, or a reply
  that breaks its schema, is not retried. A recorded failure is one
  line, with any key put out.
- `eval.toml` that does not parse is said to be unparsable and no more:
  the parser quotes the line it dislikes, which may hold a key. A file
  that cannot be read, other than for being absent, is not taken for no
  file.
- The judge's vendor (the model id's prefix) must differ from the
  answering model's; the run warns if not.
- openevals asks its judge for a `json_schema` response format, as a
  probe against a stub server showed, so the judge and the generating
  model must be ones whose provider supports structured output.
- `--max-calls` caps the model calls of a command, and a dry run
  (`--dry-run`) prints the calls it would make before any is made.

## A run

```sh
bun run eval -- run --work ~/eval --systems dorothy,lexical,full \
    --budget 8000
bun run eval -- run --work ~/eval --retrieval-only
```

For each accepted question and each system:

1. **Retrieve** within the budget (8,000 characters by default, the
   block's own default), timing it.
2. **Evidence recall**: whether any evidence id is among the first 5 and
   the first 10 items, a conversation matching by phrase.
3. **Answer**, unless `--retrieval-only` or the question is a `lookup`:
   the answering model gets the retrieved items and the question, dated
   by `asOf`, with one fixed prompt that says to answer from the items
   or say it does not know. No prompt names the question's type.
4. **Judge**: openevals' correctness judge against the reference, once
   strict (every fact of the reference, nothing contradicting it) and
   once lenient (its main point); for `abstention`, whether the answer
   declines. Each judgement keeps its score and its reasoning.

Records go to `<work>/runs/<run>/records.jsonl`, one per question and
system, written as each completes, so an interrupted run resumes with
`--resume <run>` and asks only what is missing. `<run>` is the start
time and a short hash of the questions and settings, which
`run.json` records with the models, the budget and the snapshot's
counts.

- A question other than an abstention is judged declined wrongly by a
  pattern (`declines`) on the answer, with no model asked. A
  `knowledge-update` with an older answer in its `note` costs one more
  judgement, whether the answer gives that older one.
- A failed retrieval, answer or judgement leaves the record with its
  failure, and nothing more is spent on that question and system.
  `--dry-run` counts the calls, none for a `lookup`, two for an
  abstention, three for the rest and four for an update with a `note`,
  for each system, and needs no key.
- A resume takes the systems, budget and questions from `run.json`. It
  refuses a snapshot taken at another time, or answer and judge models
  other than the run's, and says to start a new run. It asks again a
  record with a failure, and where a question and system have two
  records the last stands. A run stopped by `--max-calls` keeps its
  records and writes the report of what is done.
- A judge of the answering model's vendor warns on the error stream and
  the run goes on.

## The report

`<work>/runs/<run>/report.md`, and `summary.json` for comparison:

- accuracy by type and overall, strict and lenient, for each system;
- evidence recall at 5 and 10 by type, `lookup` included;
- abstention: how often an `abstention` question was declined, and how
  often another was declined wrongly;
- for `knowledge-update`, how often the older answer was given;
- retrieval time and characters, answer tokens and time, failed calls;
- the questions each system alone got right or wrong, by id, on strict
  accuracy, among those judged by two systems or more.

A question that should have been judged but was not, as its retrieval,
answer or judgement failed, counts as a miss in strict, lenient and, for
an abstention, declined; so a flaky system does not score higher for
its failures. Its rates are over every question owed, and its failed
calls are counted beside them.

```sh
bun run eval -- compare --work ~/eval <run> <run>
```

prints the two summaries side by side with their differences, and the
note's rule for adopting a provider: ten points of strict accuracy over
Dorothy improved, held with the smaller ingest model. The report gives
counts with every rate, as 300 questions split seven ways leave some
types small; a difference under the type's count's resolution, two
questions' worth of the smaller count, is marked as such. The
comparison covers the systems both runs hold, and strict accuracy
alone; the adoption rule is printed, not decided.

## Failures

- A command missing its `--work`, its snapshot or its questions says
  which and what to run first, and exits 1.
- A role with no key in its variable is named, with the `dotenvx set`
  command that would set it; nothing else is printed of the
  environment.
- A malformed question, a failed system call or a failed model call is
  recorded and counted in the report, never fatal; a failed call counts
  as a miss in the rates.
- An interrupted run leaves every completed record; `--resume` finishes
  it.

## Privacy

- The snapshot, questions, runs and reports hold her data in clear, in
  the work directory alone; tests use fixtures built in temporary
  directories and never read a real data directory.
- Model calls send passages of her data to the providers the user
  names; the README says so, and a local server keeps them home.
- No key reaches a file, a log, a record or a report.

## Testing

- Every unit is tested against a fixture archive written into a
  temporary directory: a dozen conversations with sidecars, appraised
  reads and knowledge files, retired ones included.
- Models are faked in tests: a fake `ChatOpenAI` returning fixed
  replies, so generation, answering and judging run without a network.
- Mining, evidence recall, the systems' retrieval and the report's
  metrics are checked against hand-counted fixtures.
- The CLI is tested for its exits and messages with a temporary work
  directory.

## Later

- The other systems: Dorothy improved, Hindsight, OpenViking, EverOS and
  Honcho, each an adapter and a replay.
- An agentic mode: the answering model drives the four MCP tools within
  a budget of calls.
- LongMemEval-S loaded as a snapshot and questions, a public anchor for
  her numbers.
- The note's two checks for a provider: a corrected memory survives a
  re-ingest, and two clients write while a second machine reads.
- A second ingest model, of 20 to 30B parameters, for providers that
  extract.

## Out of scope

- Choosing the engine: the engine spec, on this evaluation's numbers.
- Recording other harnesses' sessions: the recording spec.
- A provider contract for her chat and reviews: Model Providers.
