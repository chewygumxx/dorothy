## Verified findings

### P2: Repeated --settings silently uses the first value

Location: packages/cli/src/claude.ts:393 (mergeTheirs).

With memory settings enabled, passing --settings='{"model":"haiku"}' followed by
--settings='{"model":"sonnet"}' produces model haiku. Each iteration merges the
new user's JSON underneath values[flag], which already contains the first user's
JSON. The repository documents that Claude only uses the last --settings value.
This can select the wrong model or preserve superseded environment and permission
settings. Keep Dorothy's own overrides separate from effective user settings until
the final merge.

Evidence: /tmp/dorothy-review-cli-probe.ts, direct Bun 1.4.2 --no-env-file,
no network or real data. Actual output:

    {"repeatedSettings":["--settings={\"model\":\"haiku\",\"permissions\":{\"allow\":[\"a\"]}}"]}

### P3: Failed Claude spawn leaves private settings files behind

Location: packages/cli/src/claude.ts:810 (spawn precedes cleanup try/finally).
Related location: packages/cli/src/claude-dump.ts:67-71 (gateway cleanup gap).

A claude executable found on PATH whose shebang interpreter is missing makes real
Bun.spawn throw ENOENT. Since spawning precedes the try/finally, gateway.stop and
Launch.cleanup are skipped. The merged private settings file remains on disk and
may contain credentials from the user's settings. Cover spawning with launch
cleanup as well. Dump launches do not create merged settings files but have the
same gateway cleanup gap.

Evidence: /tmp/dorothy-review-cli-probe.ts injects a temporary HOME/PATH/runtime,
fake memory and gateway; it uses real Bun.spawn on a temporary executable naming
a nonexistent interpreter. Actual output:

    {"spawnError":"ENOENT","stopped":false,"remainingSettings":1}

Temporary fixture directory removed by the probe. Only synthetic fixture values
were used, no real credentials or .env access.
