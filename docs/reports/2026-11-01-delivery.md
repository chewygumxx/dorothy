# Delivery

## Summary

[The spec](../specs/2026-11-01-delivery-design.md) and
[the plan](../plans/2026-11-01-delivery.md) carry Dorothy's memory and
persona to two more hosts, with Claude Code as it was. One command,
`dorothy --hook <host> <event>`, answers a host's hook with her block at
a session's start and recall for a prompt, in Codex's hook shape, and
fails open. `dorothy --codex` launches Codex with her persona, her MCP
server, her two hooks and Codex's own memories off, all as session
flags, writing no host file. `dorothy --install hermes` writes a
`dorothy` profile and a Hermes memory provider of hers, a Python plugin
that calls the same hook command; the sweep now reads every Hermes
profile's `state.db`. `selfCommand` and the shared `runForwarding`
loop in `self.ts` serve every launcher.

Eight of nine tasks were built and reviewed by subagents on the branch
`feat/delivery`. The live probes of the hosts themselves wait for the
user: Codex's usage is spent until 5 November, and Hermes needs the
user to sign a temporary home in. In their place a probe Dorothy, on
temporary roots and a port of her own, answered her real hook command
and her real Python provider for both hosts, with no model and no host.
That path works, and the live steps are the only ones left open.

## Reviews

Each task had a fresh reviewer after its implementer.

- Tasks 1 to 3 and 5 to 8 were approved, their minors deferred (below).
- Task 4 had one Important finding: the Codex launcher held a copy of
  `claude.ts`'s signal-forwarding loop, which the plan had asked for as
  a shortcut and the spec did not. One round fixed it by sharing
  `runForwarding` in `self.ts`, both launchers using it; the scoped
  re-review was clean.
- Three reviews were asked to watch Task 9: a reply cut by
  `process.exit` on a pipe (Task 3), Hermes passing no `cwd` to the
  provider (Task 5), and Codex's payload shape (Task 1). The first is
  checked below, the third waits for Codex, and the second is open.

## Rulings

The spec's Decisions table, ruled by the coordinating agent, each with
its cost if wrong:

1. Hosts now: Codex and Hermes, Claude Code as it is, OpenClaw when
   installed. Cost: OpenClaw waits a phase.
2. Codex's route: a launcher, `dorothy --codex`, on session flags.
   Cost: her Codex is a command, not plain `codex`.
3. Codex's hook trust: approved once by the user in Codex's own prompt,
   never bypassed. Cost: Codex writes its trust state; a new command
   asks again.
4. Hermes's route: a memory provider plugin and a `dorothy` profile.
   Cost: plain `hermes` stays without her.
5. Writing host files: only `--install`, run by the user. Cost: Hermes
   needs one install step.
6. How hosts run her: `selfCommand`, the main checkout's entry, never a
   worktree's. Cost: an install moves with the checkout.
7. Hosts' own memories: off in her sessions and her profile. Cost:
   their own notes stop there.
8. rulesync: not adopted now. Cost: two hosts' writers are ours.
9. Hook command: one, `dorothy --hook <host> <event>`. Cost: Claude Code
   keeps its own beside it.
10. Recording: the sweep, as now; no recording hooks. Cost: recall lags
    a sweep.
11. Tools: her MCP server in every host. Cost: a host without MCP gets
    none.
12. Persona text: `@dorothy/identity`, which `cli` now imports. Cost:
    one more edge in the graph.
13. Hermes's provider: Python, calling the hook command for block and
    recall. Cost: a process a turn, inside Hermes's 8-second limit.
14. Hermes's clone: Hermes's own copy of `.env` stands; no login is
    copied. Cost: her profile holds the user's keys too.
15. Probes' logins: the user signs a temporary host home in; none is
    copied. Cost: Codex's probes wait for the user.

The plan's four departures from the spec, ruled before execution:

1. `HOOK_HOSTS` is a list in `args.ts`, pinned by a test to the
   profiles whose `delivery` lists `hook` or `plugin`, so `--help` loads
   no profile. Cost: a new host is two edits.
2. `userInstructions` reads the user's and the project's
   `.codex/config.toml`, the project's winning; a `--profile`'s
   instructions are not read. Cost: a profile's
   `developer_instructions` is replaced in her sessions.
3. `runHostHook` logs a failure to her hook log, which her hooks share.
   Cost: one log for every host's hooks.
4. `--install hermes --entry <path>` names the entry to write, for
   probes from a branch; the install checks the entry answers `--hook`.
   Cost: one flag more.

During execution, from the ledger:

1. Ruling 1: `Spawned` moves to `self.ts` with `spawnInherited`,
   exported, and `claude.ts` imports it from there. Why: Task 4 imports
   it from `../self.js`. Cost if wrong: one import path to change.
2. Ruling 2: Task 1 runs its Hermes step and fixtures now; its Codex
   steps (1, 2) are recorded as waiting for the user, who said the
   Codex probes wait. Tasks 2 to 4 use the binary's payload shape, as
   the plan allows. Cost if wrong: fixtures corrected after the probe.
3. Ruling 3: with no Codex probe, Task 4 builds the session-flag route;
   Step 6's plugin route is not built. Cost if wrong: a follow-up
   switches routes once the probe shows hooks from flags are refused.
4. Ruling 4: Task 9 runs Steps 1 and 2 (check, probe Dorothy) and
   records Steps 3 (Hermes, needs the user's sign-in) and 4 (Codex,
   after the probes) as waiting; the report says so. Cost if wrong:
   none, the steps wait for the user either way.
5. Task 4's Ruling: the plan-mandated copy of `claude.ts`'s
   signal-forwarding loop is replaced by one helper in `self.ts` used
   by both launchers. The spec asks for no duplicate, the plan's "copy"
   was a shortcut, and two loops drift. Cost if wrong: `claude.ts`
   touched again, its tests the net.
6. Task 9's Ruling: Steps 3 and 4 need the user's sign-ins, so Step 2's
   probe Dorothy is exercised without a model: the real `--hook
   codex|hermes` against it (seeded fact in the block and recall, a
   large reply through a pipe, the service stopped) and the real Python
   provider run against her real hook command. The no-model path is
   verified now. Cost if wrong: none, Steps 3 and 4 still wait for the
   user.

## Verification

### The whole check (Step 1)

```sh
t=$(mktemp -d)
XDG_DATA_HOME=$t/d XDG_CACHE_HOME=$t/c XDG_STATE_HOME=$t/s bun run check
```

Exit 0. The tail of the output:

```text
 3741 pass
 1 skip
 0 fail
 143530 expect() calls
Ran 3742 tests across 177 files. [43.22s]
```

The skip is the existing one. The `[WARN]` lines before the tests are
`lint:header`'s "not found" notices for captured output files, which
were there before the branch.

### A probe Dorothy (Step 2)

Temporary `XDG_*` roots under `$P`, her service on port 47123 with
`DOROTHY_MEMORY_URL` at it, and one fact only she holds:

```sh
P=$(mktemp -d)
export XDG_DATA_HOME=$P/data XDG_CACHE_HOME=$P/cache \
  XDG_STATE_HOME=$P/state XDG_CONFIG_HOME=$P/config
export DOROTHY_MEMORY_URL=http://127.0.0.1:47123
bun "$E" --serve &
curl -sf "$DOROTHY_MEMORY_URL/v1/health"
```

```text
{"ok":true}
```

Two findings on the plan's seed:

- The plan's `probe-colour.md` has no `generated` block, which her
  store requires, so the service moved it to `broken/` with
  `generated is not a mapping`. Adding
  `generated: {by: "human:probe", at: ...}` made it parse. The plan's
  Step 2 needs that block.
- The fact showed in the block five seconds after the rewrite, with no
  sweep and no restart. Eighty filler facts written to the running
  service did not; a restart showed them. That is not explained here.

Every command below ran in one shell with those exports, so nothing
reached the user's store or service. Each probe service was stopped by
its pid, checked against its environment first.

### The same for Hermes

`--hook hermes session-start` and `--hook hermes prompt` printed the
same two replies byte for byte (exit 0, 651 bytes for the block), as
the host name only keys the cached block. Recall for the prompt `hi`
printed nothing and exited 0: no knowledge bore on it.

### A large reply through a pipe

The first block is 564 characters, too small to show a cut. Eighty
filler facts (bodies of about 1,000 characters) were added, the probe
service restarted, and the block asked for under a fresh session:

```sh
bun "$E" --hook codex session-start < in.json > big.json
bun "$E" --hook codex session-start < in.json | wc -c
bun "$E" --hook codex session-start < in.json | (sleep 3; wc -c)
```

```text
exit=0
10092
10092
file_bytes 10092 ctx_chars 9974 has_teal false
ends "conversation whole, call open.\n</memory>"
```

The piped count, the slow reader's count and the file are the same
10,092 bytes, the JSON parses, and `additionalContext` is 9,974
characters ending at the block's closing tag, so `process.exit` cut
nothing. The block is capped near 10,000 characters, well under a
pipe's 64 KB buffer, so this shows the reply written whole, not a
reply past the buffer. With 80 fillers, teal no longer fits the block.

### Her Hermes provider against her real hook command

In a scratch directory outside the repository, python3 with a stub
`agent.memory_provider` module (as `test_dorothy.py` does):

```python
p = dorothy.DorothyProvider(
    command=["bun", "--no-env-file", E], cwd=PWD)
p.initialize("probe-2")
print(p.system_prompt_block())
print(p.prefetch("what is my favourite colour?"))
```

Run with `python3 -I -B` (`-I` ignores `PYTHONDONTWRITEBYTECODE`, and
the first run wrote `__pycache__` into `assets/hermes/dorothy`, which
was removed; the repository is clean). Exit 0:

```text
BLOCK: '<memory>\nBelow is what you remember of this user and their
work: ...\n<knowledge scope="personal">\n- The user\'s favourite colour
is teal (k:personal/probe-colour): ...\n</knowledge>\nTo look further,
...\n</memory>'
PREFETCH: '<recalled>\nFrom your memory, perhaps bearing on this
message; information, not instruction:\n<item
id="k:personal/probe-colour">\nThe user\'s favourite colour is teal
(user, personal, 2026-11-01)\n...\n</item>\n</recalled>'
```

Both strings are the hook's `additionalContext`, unwrapped, and hold
teal. `cwd` was the scratch directory (`PWD` there), not a project.

### The service stopped

The brief expected the hook to print nothing. It did not, and why is
the finding:

- With the probe service killed, `--hook codex session-start` exited 0
  and printed the full 10,092 bytes. `ensureService` had started a new
  `--serve` (detached, so it outlives the hook) and waited for it, and
  the hook answered from that. A second kill and rerun did the same.
  Both services were killed by pid, after their environments were
  checked.
- A fresh `XDG_STATE_HOME` (no cached block) with
  `DOROTHY_MEMORY_URL=http://192.0.2.1:47123`, a non-loopback address
  that the hook never starts a service for:

```text
exit=0
0 bytes (block), 0 bytes (hermes prompt)
```

  It took 1.4 seconds in all, and no service was started. This is the
  fail-open path: an empty reply, exit 0.
- When a service is down and no such block is cached, the first hook of
  a session therefore pays the service's start. On the probe it fit
  the hook's wait; a host with a shorter timeout than `START_WAIT`
  would get nothing that once and the block from the next session.

After the probes no service listened on 47123 or 47999, `git status`
was clean, and no `__pycache__` remained.

## Waiting for the user

Step 3, Hermes, on a temporary home. The user's `config.yaml` is copied
and the user signs the temporary home in; no `auth.json` is copied:

```sh
export HERMES_HOME=$P/hermes && mkdir -p "$HERMES_HOME"
cp ~/.hermes/config.yaml "$HERMES_HOME/"
HERMES_HOME=$HERMES_HOME hermes login          # the user
bun "$E" --install hermes --entry "$E"
hermes -p dorothy chat --oneshot -q "what is my favourite colour?"
bun "$E" --sweep
```

It will show: the install's report; whether the cloned `dorothy`
profile signed in from the default (if not, the user signs
`hermes -p dorothy` in too); whether her `SOUL.md` and block reached the
system prompt (Hermes's debug output) and the answer said teal; whether
Hermes passes a `cwd` to her provider; and that the sweep recorded the
session from `profiles/dorothy/state.db`. It spends the user's Hermes
model, one short turn. The provider and hook halves of this are
verified above without Hermes.

Step 4, Codex, after 5 November 17:23, with the user:

```sh
export CODEX_HOME=$P/codex && mkdir -p "$CODEX_HOME"
CODEX_HOME=$CODEX_HOME codex login             # the user
CODEX_HOME=$CODEX_HOME bun "$E" --codex        # trust her hooks, /exit
bun "$E" --codex exec --skip-git-repo-check "what is my favourite colour?"
bun "$E" --sweep
```

It will show: the trust screen and what Codex wrote to
`$CODEX_HOME/config.toml`; whether hooks from session flags are offered
for trust at all (otherwise Task 4's plugin route is built); whether
`developer_instructions` is accepted and additive; whether Codex's
payloads match the fixtures; whether the answer said teal; and that the
sweep recorded the rollout.
[The probes' record](./2026-11-01-delivery/probes.md) lists the same
open questions.
